# 大模型技术全景：从 Token 到智能体

把大模型当成"会思考的黑箱"，讨论就没法继续。更有用的视角是：它是一条**由若干可拆解、可测量、可替换的环节组成的流水线**——文本进来，被切成 Token；Token 变成向量；向量在几十层注意力里被反复改写；最后输出下一个 Token 的概率分布。

这条流水线的每一段都有自己的瓶颈、成本和调参空间。下面按数据流动的顺序走一遍，尽量讲清楚"是什么、为什么这样设计、工程上要注意什么"。

## 一、分词：文本变成 Token

模型不认识"字"，只认识 Token——一个介于字符与词之间的子词单元。

常见做法是**子词分词**（BPE、Unigram 等）：从字符起步，反复合并出现频率最高的相邻片段，得到"词表大小"与"覆盖率"之间的折中。

几个容易踩的点：

- **Token 不等于字，也不等于词。** 常见英文词可能就是一个 Token，罕见词会被拆成多段；标点和空白同样占 Token。
- **计费和上下文预算按 Token 算**，不按字符数算。同一段内容在不同语言、不同分词器下，消耗的 Token 数可以相差不少。
- **分词器一旦训练完就固定**，它是模型的一部分。换分词器等于换模型。

## 二、嵌入与位置：Token 变成带位置的向量

每个 Token 通过一张查找表映射为一个稠密向量（embedding）。这个向量的方向编码了语义——语义相近的 Token，向量夹角更小，所以可以用余弦相似度衡量"像不像"。

但注意力本身是**置换不变**的：把输入的 Token 打乱，注意力的计算结果不变。所以必须额外注入位置信息。做法经历了从绝对位置编码到相对位置编码的演进，目前主流是**旋转位置编码（RoPE）**：把位置信息编码成对向量的旋转操作，使注意力点积天然带有相对位置的成分，对长度外推也更友好。

## 三、注意力：真正干活的地方

Transformer 的核心是**自注意力**。每个位置的向量被投影成三个角色：

- **Query（Q）**：我在找什么
- **Key（K）**：我能提供什么
- **Value（V）**：我实际携带的信息

计算方式：

$$\mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V$$

直觉上：每个位置拿自己的 Q 去和所有位置的 K 做点积，得到一组"该关注谁"的权重；再用这组权重对所有 V 加权求和。

几个关键设计：

- **缩放因子 $1/\sqrt{d_k}$**：防止维度变大时点积方差过大、softmax 饱和成近似 one-hot，导致梯度消失。
- **多头注意力**：把向量切成多份并行计算，让不同的头关注不同类型的关系（句法、指代、位置等），最后拼接。
- **因果掩码**：生成式模型（decoder-only）不允许看到未来 Token，所以在 softmax 前把上三角位置置为 $-\infty$。

**复杂度**：自注意力对序列长度 $n$ 是 $O(n^2)$ 的时间和显存开销。这是长上下文一切困难的根源——序列翻一倍，注意力开销大约翻四倍。

层与层之间还有前馈网络（FFN）、残差连接和归一化（近年多用 RMSNorm），激活函数常用 SwiGLU 一类门控结构。在标准 Transformer 里，FFN 往往占据参数量的大头。

## 四、预训练：把知识压进参数

预训练的目标出奇地简单：**预测下一个 Token**。给定前文，模型输出整个词表上的概率分布，用交叉熵损失去逼近真实的下一个 Token。

仅靠这一个目标，模型就学会了语法、事实、推理套路和代码风格——因为这些能力都有助于降低"下一个 Token"的预测误差。

规模法则（Scaling Laws）给出了一条经验规律：**损失随算力、参数量、数据量的增长呈幂律下降**，而且在很宽的范围内相当可预测。这直接决定了行业的资源分配方式。

后续的 Chinchilla 类工作进一步指出：**参数量和训练数据量应当按比例同步增长**。换个说法，很多早期模型不是"不够大"，而是"喂得不够多"——同样的算力，更小的模型配更多的数据，效果可能更好。

数据工程的权重常被低估：去重、质量过滤、领域配比、清洗顺序，都会实打实地反映到最终能力上。

预训练结束后，模型是一个很强的"续写器"——它能把一段文本自然地接下去，但不一定按你的指令做事。

## 五、对齐：从"会续写"到"听得懂话"

要让模型"回答问题"而不是"续写问题"，需要对齐阶段：

1. **监督微调（SFT）**：用写好的"指令—回答"示范数据继续训练，教会它对话格式与指令遵循。
2. **奖励建模 + 强化学习（RLHF）**：让标注者对多个候选回答排序，训练奖励模型去拟合人的偏好；再用强化学习（如 PPO）优化策略模型，使其输出更受奖励模型青睐。
3. **直接偏好优化（DPO 等）**：跳过显式奖励模型，直接用偏好对构造损失，训练更稳定、工程更简单，因此被广泛采用。
4. **AI 反馈（RLAIF / 宪法式方法）**：用模型按一套明确原则去评判与生成偏好数据，降低人工标注成本。

需要清醒的一点：**对齐优化的是"人喜欢什么"，不是"什么是真的"**。一个被优化得足够讨喜的模型，反而可能更自信地编造内容。这直接引出了后文的幻觉问题。

## 六、推理：Token 是怎么一个接一个吐出来的

### 自回归解码

生成是逐 Token 的：每步前向算一次，取一个 Token，追加到输入，再算下一步。这决定了**输出长度直接线性影响时延**。

### 采样策略

- **贪心**：每步取概率最高的 Token。确定、可复现，但容易重复、呆板。
- **温度**：对 logits 做缩放。温度越低越保守，越高越随机。
- **top-k / top-p（核采样）**：只在概率最高的若干候选里采样，砍掉长尾噪声，兼顾多样性与稳定性。
- **重复惩罚**：抑制已出现过的 Token，缓解复读。

### KV Cache：推理加速的核心

自回归解码时，前面 Token 的 K、V 每步都在重复计算。把它们缓存下来，每步只需计算新 Token 的 Q、K、V，再与缓存拼接——这就是 KV Cache。

代价是显存。KV Cache 的大小近似为：

$$2 \times L \times H_{kv} \times d_{head} \times n \times B \times \text{字节数}$$

其中 $L$ 是层数，$H_{kv}$ 是 KV 头数，$n$ 是序列长度，$B$ 是并发批大小。它随**序列长度和并发数线性增长**，在长上下文场景下往往比模型权重还占显存。

顺带一提，**分组查询注意力（GQA）** 让多个 Query 头共享一组 K/V 头，正是为了压缩上面这个 $H_{kv}$。

### 显存与吞吐的工程化

- **连续批处理（Continuous Batching）**：请求随到随批，不等整批结束，显著提升吞吐。
- **PagedAttention**：把 KV Cache 切成固定大小的块、用块表寻址，像操作系统管理虚拟内存那样消除碎片，并支持前缀共享。
- **量化**：把权重（有时含激活）从 FP16 压到 INT8 / INT4，用少量精度换显存与带宽。
- **投机解码**：用小模型快速草拟若干 Token，再让大模型一次并行验证，接受命中的部分。
- **并行策略**：张量并行（层内切）、流水并行（层间切）、数据并行（副本切），用于跨卡放大模型。

## 七、新范式：先想，再答

上述都是"一次前向"的推理。近两年一个明显的转向是：**把算力从训练阶段挪到推理阶段**。

- **思维链（CoT）**：让模型先写出中间步骤再给答案，明显改善多步推理类任务。
- **测试时计算（Test-time Compute）**：允许模型回答前"多想一会儿"——生成长推理链、采样多条路径再投票或验证。
- **以可验证任务做强化学习**：数学、代码这类能自动判对错的领域，可以直接拿"最终答案是否正确"当奖励，训练模型产出更长的推理过程。

代价同样直接：**延迟和成本成倍上升**。所以它适合"精度远比时延重要"的任务，而不是所有场景。

## 八、应用层：让模型接上外部世界

模型参数里的知识是静态的、有截止日期的。应用层的核心工作，就是给它接上外部的、实时的、私有的信息。

### 检索增强生成（RAG）

流程：**切片 → 向量化 → 检索 → 重排 → 组装上下文**。

工程上真正的难点不在"能不能检索"，而在这些地方：

| 环节 | 常见问题 | 应对 |
| :--- | :--- | :--- |
| 切片 | 切碎语义、切断表格与代码 | 按结构切、设重叠窗口、保留标题层级 |
| 检索 | 纯向量检索漏掉精确匹配（编号、专有名词） | 向量 + 关键词的混合检索 |
| 排序 | 召回了，但没排到前面 | 加交叉编码器重排 |
| 组装 | 上下文塞太多，中段信息被忽略 | 控制条数、按相关度排序、给出引用 |
| 兜底 | 检索为空时硬编 | 明确回答"资料里没有" |

**RAG 不能根治幻觉**：它只是把"凭空编"换成"可能误读材料"。检索错了、材料本身矛盾、模型过度概括，都会继续出错。

### 工具调用与智能体

- **工具调用（Function Calling）**：把外部能力（搜索、计算、数据库、设备 API）描述成结构化接口，让模型输出调用参数。
- **智能体（Agent）**：在"感知 → 决策 → 行动 → 观察"的循环里反复调用模型与工具，并维护任务状态。
- **真正决定成败的是循环之外的部分**：状态管理、失败重试、幂等、超时、权限边界、成本上限。

### 上下文工程

比起"提示词工程"，更准确的描述是**上下文工程**：决定在这一步前向里，究竟把哪些信息放进去（系统指令、检索结果、历史对话、工具返回、记忆摘要），以及以什么顺序放。模型输出的质量，很大程度上在这一步就决定了。

## 九、评估：最容易被糊弄的一环

- **离线基准**：可复现、便宜，但存在**数据污染**——训练数据里见过题，分数就会虚高。
- **人工评估**：贴近真实，但慢、贵，标注者之间的一致性难以保证。
- **LLM 作为裁判**：成本低，但有已知偏差（偏好长回答、偏好与自己风格相近的输出、位置偏差）。
- **线上 A/B**：最可信，代价是周期长、需要流量。

一套务实的顺序是：**先定义任务成功率**（能不能把事办成），再同时盯时延与成本，最后才看基准分数。

## 十、局限与风险：写进设计里，而不是写进免责声明里

- **幻觉**：语言模型的训练目标是"最大化下一个 Token 的似然"，不是"断言事实"。流畅与正确并不等价。
- **上下文长度**：标称支持的长度不等于有效利用的长度。经验上，模型对上下文中段信息的利用率明显低于首尾。
- **确定性**：同样输入，由于采样与浮点累加顺序，输出不保证逐字一致。想复现要靠固定随机参数。
- **知识与时效**：参数里的知识会过期，除非外接检索。
- **安全**：提示注入（把恶意指令藏在被检索的文档或网页里）、越狱，以及通过工具调用导致的数据外泄，都需要在架构层设防，不能只靠提示词。
- **成本与时延的物理约束**：上下文长度、并发数、Token 量都是要付钱的，预算必须算进工程方案。

## 十一、给工程实践的十条建议

1. 先把任务定义成**可测量的成功率**，再谈选型。
2. 能靠检索解决的，不要靠微调：**知识用 RAG，行为用微调**。
3. 上下文优先：同样的模型，喂对信息比换更贵的模型更有效。
4. 结构化输出要**校验**，模型给的 JSON 也可能不合 schema。
5. 永远设计**兜底路径**：检索为空、工具超时、模型拒答时，用户看到什么。
6. 把**时延拆开量**：首 Token 时延与总时延是两件事，体验主要由前者决定。
7. 上线前跑**回归集**：把踩过的坑固化成用例，防止改提示词改崩。
8. 记录**完整调用链**（输入、命中文档、工具参数、输出、Token 消耗），否则线上问题无法定位。
9. 给**成本设硬上限**：单次请求 Token 上限、重试次数上限、循环步数上限。
10. 把不确定性当**工程问题**处理——用检索、校验、兜底和评估去覆盖它，而不是指望模型"这次别出错"。

## 结语

大模型的能力看起来像涌现，但拆开看，每一层都可以被理解、被测量、被调试。真正拉开差距的，通常不是"用了哪个模型"，而是这些枯燥的部分：数据、上下文、评估、成本、失败处理。
