# 予念 iOS：从零到 Beta 3，以及我们撞过的每一堵墙

这篇是 iOS 端开发者的手记。

Android 版予念已经跑了很多个版本，而 iOS 端是从**一行 Swift 都没有**开始的。第一笔 iOS 提交在 2026-10-05，Beta 3 在 10-12 发布，到今天（11-09）一共 214 个提交、49 个版本标签。这篇文章想做两件事：**把进度如实说清楚**，以及**把撞过的墙全部列出来**——包括那些至今还没翻过去的。

之所以要写后者：踩坑记录如果只留在提交信息和聊天记录里，下一个人（或者下一轮的我）一定会再踩一次。

## 一、先给结论

| 项 | 现状 |
| :--- | :--- |
| 当前版本 | **Beta 3**（App 内 `1.0.0 (3)`，标签 `v1.0.0-ios-beta.3`） |
| 分发方式 | **未签名 IPA** + 你自己用 Apple ID 自签（免费账号可用，7 天有效期） |
| 工程规模 | 197 个文件 / 53,344 行（Swift 140 个 / Python 37 个） |
| 测试 | 45 个测试文件、541 个测试函数 |
| 本地验证关卡 | **34 道，全绿**（一键驱动） |
| 最低系统 | iOS 17.0 |

能用的部分：对话、流式回复、思考过程、记忆、世界书、技能库、角色卡导入导出、表情库、生图、备份导入导出、TTS 朗读、通知与角标、多线路 API 配置。

还不能用的部分，见第五节，一条不藏。

## 二、路线：为什么是原生 SwiftUI，而不是共享 UI

移植 iOS 有两条主流路线。我们选了看起来更"笨"的那条。

**路线 A：Compose Multiplatform 共享 UI。** 听起来很美——同一套界面代码跑两端。但实测下来有三个硬障碍：

- UI 层 **84.1% 的行处于硬耦合**（直接引用 `androidx.compose.*` 或 Android 平台 API）；
- **22 / 27 个 ViewModel 是 `AndroidViewModel`**，而 CMP 根本不提供这个类；
- 25 个 Gradle 模块的 KMP 改造会**反向波及 Android 侧**，和仓库 AGENTS.md 里「架构最小变更原则」直接冲突。

CMP 真正可行的范围只有「共享设计系统，不共享页面」——而那个量级（47 个文件 / 6,630 行）的收益，抵不过把 141 个 Composable 全部 commonMain 化的成本。

**路线 B：SwiftUI 原生壳 + 复用 Rust Agent。** 我们选了这条。它成立的关键是一个实测发现：

> 流式对话的**生产路径已经在 Rust 里**。SSE 解析、重试、交付守卫、多轮工具决策全部下沉在 `lianyu_agent` 这个 crate 中；Kotlin 侧那套约 300 行的 SSE 实现，**全仓只有测试在引用，是死代码**。

所以 iOS 端理论上只要做两件事：**重建 UniFFI 的 Swift 绑定**，**实现 `ToolHost` / `StreamSink` 两个回调**，就能白拿完整的流式对话能力。

而且这个 Rust crate **零平台假设**——全 crate 没有一处 `cfg(target_os)`，58 个 UniFFI 导出实体里 49 个是纯逻辑，生产代码只读 2 张表。移植它不需要改一行 Rust。

代价是：界面要重写。这个代价我们认了，后面第四节会说为什么这其实是好事。

## 四、瓶颈

下面按性质分类。前三类是技术问题，第四类是方法问题——而第四类是最难缠的。

### 4.1 环境：没有 Mac 这件事，比想象中贵

整个项目在 **Windows + WSL2(Arch) + xtool** 上完成构建、签名与真机安装，全程没有 Mac。可行，但代价是持续的：

**① CI 不是可选项，是必需品。** 即使只编 Rust Agent，也必须用 macOS + iOS SDK。本地能做的只有契约类检查（schema、字面量、绑定签名、SQL），编译这件事只能交给 GitHub Actions 的 macOS runner。

**② 工具链版本会咬人。** XcodeGen 必须锁在 2.44.0——最新版生成的 project format 77，Xcode 15.4 读不了。这类问题在本地完全不可见，只在 CI 上炸。

**③ 想要 iOS 26 的 API，就得换 runner。** `macos-15` 自带 Xcode 16.4，**没有 iOS 26 SDK**，连 `#available(iOS 26.0, *)` 里的 `.glassEffect` 都编译不了。这不是"为了用新东西而升级"，是没 SDK 就写不了。顺手加了一步打印 `xcodebuild -version` 和 `-showsdks`——之前几轮都在猜 runner 带什么版本，猜错了两次。

**④ 看不见画面。** `idevicescreenshot` 和 `xtool launch` 都因为 **Developer Disk Image 未挂载**失败，本地没有模拟器。这意味着**任何界面问题都只能靠用户截图反馈**。我们后来找到一条替代通道：让 App 自己在启动时打一行几何日志，用 `idevicesyslog` 抓回来——这条通道在 4.4 那个事故里救了命。

**⑤ 本地 Swift 和 CI 的 Swift 不是同一个 Swift。** 本地 WSL 是 Swift 6.4，CI 是 Xcode 自带的编译器。有些坑只有 CI 会暴露：

```
error: failed to produce diagnostic for expression; please submit a bug report
```

这**不是普通类型错误，是编译器崩溃**（连诊断都产不出来）。第一轮我们误判成"自动闭包 + 嵌套调用"的表达式问题，拆开写了；第二轮才发现真正的根因是**名字**——我们把方法、参数、局部变量都命名为 `override`，而那是 Swift 的声明修饰符关键字。改个名字就好了（`override` → `voiceOverride`）。

教训写进注释了：**本地构建通过 ≠ CI 能过**，新写法要贴着仓里既有、CI 已在编的形状写。

**⑥ 一个 C 头文件，逼出了自建 PBKDF2。** 备份文件是密码加密容器，Android 侧用 `PBKDF2WithHmacSHA256`（10 万次迭代）。iOS 上 `CCKeyDerivationPBKDF2` 在 CI 上稳定报 `cannot find in scope`——`import CommonCrypto` 本身是成功的（否则会报 no such module），所以是符号可见性问题。target 级、工程级 `OTHER_LDFLAGS` 都试过，两次都没解决。

在没有 Mac 的情况下第三次继续猜根因是不负责任的。于是我们**用 CryptoKit 自建了 PBKDF2**，只依赖 `HMAC<SHA256>`。但移植前先做了一件事——**证明等价性**：

```
Python 手写 PBKDF2-HMAC-SHA256  vs  JDK 21 PBKDF2WithHmacSHA256
→ c5c7a93cdb10d03d9d79c02e31e154cbc7cc3ab85f3637be1adcfea3ed346280
→ 逐字节一致（迭代 100000 / 盐 16 字节 / 输出 32 字节）
```

Swift 实现是那份 Python 的直译，参数逐字沿用 Android 侧。现在有确定性夹具兜着：错误密码必须失败、盐长度错必须失败、篡改密文与篡改 tag 都必须失败。

**⑦ 本地不编测试目标。** `xtool` 只编 App，不编 `YuNianTests`——**测试文件的编译错误只有 CI 会拦**。这个坑吃过一次（`a8e3d769`），代价是一轮 CI 的等待时间。

### 4.2 平台硬边界：iOS 真的没有

这类问题没有"努力一下"的解法，只能改产品语义，或者明确说不做。

| Android 的做法 | iOS 的处境 | 我们的决定 |
| :--- | :--- | :--- |
| 前台服务 + 心跳保活，熄屏也不掉线 | **没有后台常驻进程**，那套 FGS / Worker / WakeLock 链路无法移植 | QQ / 微信机器人**不做** |
| `AlarmManager` 8 分钟精确闹钟自续链 | 无法在客户端维持 8 分钟级心跳，也无法保证任何时间精度的本地调度 | 调度**上移到服务端**（尚未接入） |
| 病娇模式：读 `UsageStatsManager` + 枚举已安装应用 | iOS 无对应 API | **不做** |
| 4 家厂商推送通道 | 换 APNs，但**免费 Apple ID 不能启用 Push capability** | 阻塞在 $99/年 |

第三条尤其要说清楚：病娇模式在 Android 上是靠"读你最近用了哪些 App"来实现的，这在 iOS 上不是"没做"，是**系统根本不给你这个能力**。

「主动找你」也一样。Android 侧它是「服务端定时 → 推送 → 客户端渲染」，看起来能移植；但免费账号拿不到 APNs，**这个功能在付费前完全无法验证**——既不能自测，也无法让用户试用。

所以 iOS 上的「主动找你」目前只能退化成：**本地定时提醒 + 用户点开**。这条限制已经写进了设置页，不装作是完整的主动消息。

> [!WARNING]
> 还有一个容易被忽略的坑：免费 Apple ID 签出来的 App **只有 7 天有效期**。对 AI 伴侣这类需要长期陪伴的产品，这意味着用户每周都要重新签一次。**免费自签名不是可行的分发方式**——它只适合"我想试试"。

### 4.3 跨端契约：最危险的是「不报错的错」

这一类是我们踩得最多、也最该被记住的。它们的共同特征是：**程序不崩溃、测试能过、界面正常，但结果和 Android 不一致。**

最典型的一次：`MessageRepository.ConversationType` 被写成了 `"COMPANION"` / `"GROUP"`，而 Android 实际存的是业务字面量 **`"chat"` / `"group"`**（小写，不是枚举名）。

这个错误隐蔽到什么程度？——我们的 SQL 验证脚本里**也写了同样的错值**，于是插入与查询**自洽**，64 项断言全过。**自洽不等于忠实。**

> [!IMPORTANT]
> 这件事之后我们立了一条规矩：所有跨端字面量必须来自**唯一来源**（`Tools/contracts.py`，全部从 Android / Rust 源码推导），任何脚本都不得再硬编码这些取值。重复硬编码正是那次事故的根因。

同类的问题，我们一共修了 13 项。挑几个印象最深的：

**① 大小写契约错位（用户可见 bug）。** 用户反馈"回复为什么是英文"，实际那句英文是**思考过程**，被当成了会话列表的最后一条消息显示。

| 侧 | 写法 | 结论 |
| :--- | :--- | :--- |
| Android `@SerialName("reasoning")` | 小写 | 那是**备份 JSON** 用的 |
| Android `fromMessageType(v) = v.name` | **`"REASONING"`** | 那才是 **Room 落库**的值 |
| iOS 写入（错） | `"reasoning"` | **自己写的行，自己的 SQL 排不掉** |
| iOS 过滤（对） | `NOT IN ('REASONING', ...)` | 对的，但和自己的写入对不上 |

修法是两侧一起：写入改成大写，过滤改成大小写不敏感（这样用户设备上已有的小写老行、以及从 Android 导入的大写行都能正确处理）。并加了 4 条测试 + 5 条关卡断言防退化。

**② `AUTOINCREMENT` 传 0 会 REPLACE 掉上一条。** 新建记忆时把 `id` 绑成 `0`，而 SQLite 把 `0` 当作**合法的 rowid 0 显式插入**——于是第二次新建就 REPLACE 掉第一条，**记忆永远只剩一条**。Room 对 `@PrimaryKey(autoGenerate = true)` 绑定的其实是 `nullif(?, 0)`。

**③ 归档语义写反了。** 我们按 `ORDER BY timestamp ASC LIMIT count` 实现，也就是"移走最旧的 N 条"；而 Android 是**裁到 N 条**（先取最新 N 条里最旧的那条做边界，归档严格早于边界的行）。两者在消息数远大于阈值时结果相同，但在**消息数少于阈值**时差别是灾难性的——LIMIT 写法会把不足 5000 条的会话**整段清空**。

这个错误是被"按 Android 原文写测试"暴露的：我们先前用 LIMIT 语义写测试，与错误实现共享了同一个误解。

**④ 一个我自己定的数字。** 回合上限 `maxRounds` 我们写成了 16，理由是"避免 0 被 Rust 兜底成 1"——意图没错，但**取值是我自己定的**。Android 主对话路径用的是 6。这个值直接决定"模型一个回合最多能调几轮工具"，调大会导致同一问题反复调工具、成本与时延上升。

**⑤ UTF-16 长度。** Kotlin 的 `text.length` 是 **UTF-16 代码单元数**，Swift 的 `String.count` 是**字符数**。对含 emoji / 组合字符的文本两者不同，用 `count` 会报出与 Android 不一致的剪贴板长度。

**⑥ 布尔值的存储形态。** 设置存成 `"1"` / `"0"`，读取却用了 `Bool(raw)`——而 **Swift 的 `Bool(String)` 只认 `"true"` / `"false"`**，遇到 `"0"` 一律返回 `nil`。症状是：用户关掉"回复提醒"，重进设置又变成开的。单看界面像"设置没保存"，很难联想到是解析问题。

**⑦ 一个"直觉是对的、但语义是错的"例子。** 我们发现 `ContentFilter.checkInput` 只有实现、没有调用，第一反应是"输入安全检查应该每回合都做"。读了 Android 的实际代码后，语义完全相反：

```kotlin
if (apiConfigRepository.getActiveEnabledConfig() == null && !hasCompanionBoundConfig()) {
    for (msg in contentBatch) {
        val inputCheck = runCatching { ContentFilter.checkInput(msg) }.getOrNull()
        if (inputCheck == null) { Error("安全检查异常"); return null }
        if (inputCheck.isViolating) { BanManager.recordViolation(...); return null }
    }
    Error("请先配置API：我 → API设置 → 添加密钥"); return null
}
// 有配置时：直接进入生成，不检查输入
```

也就是说，过滤只在**完全没有 API 配置**时执行，作用是"在报『请先配置API』之前先挡一把"。按直觉改成每回合检查，会拦住 Android 会放行的输入——真实的跨端不一致，症状是「iOS 上某些话发不出去」且无法归因。

**⑧ 一个我们决定「不修」的问题。** 安全基线数据里的中日文条目是乱码——实测 `keywords` **94/284** 条、`filterPatterns` **317/583** 条是「UTF-8 字节被按 Latin-1 解读」的双重编码产物。这意味着 **Android 的内容过滤在 CJK 维度上实际不生效**（英文部分 266 条正常）。

iOS 侧**如实保留**了这个缺陷。理由是：如果 iOS 单方面修复，它的过滤强度会**高于** Android——这属于产品/安全决策，不该由移植方单方面改变。修复是确定性的（`s.encode('latin-1').decode('utf-8')`），Swift 侧的还原函数已实现并有金标单测，但**启用开关前必须同时修改 Android 侧**。

### 4.4 UI：逐像素复刻是死路

这一节是全篇最贵的一课。

iOS 端最初 5,505 行视觉代码（`Views/` 3,967 行 + `Theme/` 1,538 行）**已被整体废弃**。废弃原因不是 bug 多，而是**指导方针错了**：

> 旧方针：**逐条复刻 Android**。每个数值都在注释里标着 Kotlin 行号。

这条方针在结构上保证了三种必然的坏结果，而且**每一种都真实发生了**：

| 必然结果 | 实际例子 |
| :--- | :--- |
| 把 Android 的**权宜之计**当规格抄 | 一个叫"液态玻璃"的组件，逐条复刻 Android 手搓的假折射，而 **iOS 26 有原生 `.glassEffect`** |
| 把 Android 的**层级机制**硬搬到没有对应物的平台 | `GlassPageScaffold` 复刻 Kotlin 的 `layerBackdrop`，注释自己写着"在 SwiftUI 无对应物" |
| 逐字段转写产生**静默错位** | `textTertiary: Palette.darkElevated` —— 把背景色当成了文字色，实测对比度 **1.41:1**（正文要求 ≥4.5） |

新方针只有一句话：**原生 iOS 优先。凡是 iOS 26 有原生 API 的，一律用原生；不自绘。**

这条方针还带来一个副产品：**跨端一致由产品语义保证，不由像素保证。** 同样的信息、同样的流程，但材质、圆角、间距可以不同。想通这一点之后，重构才真正停下来。

#### 那个把整页撑宽的 520

讲一个真机事故，因为它说明"看不见画面"有多贵。

用户连续两轮反馈"内容被裁"——标题缺第一个字、右列时间被切、头像缺角。我们按"整行超宽""自绘组件不可靠"两个假设改了两轮，**都没修好**，因为看不到渲染结果。

第三轮换了办法：**让 App 自己报几何**。真机日志：

```
geometry screen 402x874  window 402x874  safeArea(62,0,34,0)   ✓ 系统级正常
probe root-tabs     size=402x778  origin=0,62                   ✓
probe list-sessions size=520x623  origin=-59,168                ✗ 宽 520、原点 -59
```

根因：画布的光源写了 `.frame(width: 520, height: 520)`，并且**与内容并列放在 `ZStack` 里**。`ZStack` 的尺寸取最大子视图的 ideal size——于是画布把整页撑到 **520pt 宽**，而屏幕只有 402pt，`List` 跟着变成 520 宽并被居中，左右各溢出 59pt 被裁。

这和用户看到的现象逐条吻合：标题缺字、右列被切、头像缺角，而**导航栏里的系统搜索框正常**（它不在这个容器里）。"系统控件正常、内容被裁"正是**容器被撑宽**的指纹。

修法：光源与颗粒全部改用 `.overlay`（overlay 不参与父视图尺寸计算）。修后日志 `size=402x623 origin=0,168`。

> 教训写进了设计文档：**装饰层与内容同层时，装饰的尺寸就是布局的尺寸。** 任何"看起来只是背景"的东西，都要问一句：它会不会参与父容器的尺寸计算？

#### Liquid Glass 是功能图层，不是美化材质

Apple HIG 里写得很清楚：Liquid Glass 属于**控制层**，**禁止用在内容层**。我们一开始把它当"高级背景"用，在 8 个卡片上做了玻璃——结果是每块都是玻璃 ⇒ 没有一块读起来像玻璃，外加 8 个独立模糊同时合成，以及"内容"与"导航"变成同一材质、眼睛分不出哪里能点。

现在的规则是：**一处玻璃 = 一处控制。** 玻璃是稀缺资源，满屏玻璃等于没有玻璃。

顺带做了一个分水岭：iOS 17–25 走 `.ultraThinMaterial`（旧原生材质体系），iOS 26+ 走 `.glassEffect`。默认按系统版本自动选，也允许用户在「我」页覆盖。

#### 还有两个"看起来是 bug、其实是平台语义"的坑

- **通知时间越界不报错。** `UNCalendarNotificationTrigger` 拿到 25:61 不会抛异常，只是**静默不响**。表现为"提醒设了但从来不响"。现在越界时间必须夹取，且有测试锁住。
- **表情清单里的括号。** 用户从 Word 复制的清单常见「全角开、半角闭」——`（小猫…稀罕物)`。原实现按"配对宽度"找闭合括号，找不到本条的，就一路找到**下一条**的 `）`，把中间整条 URL 当成名字吞了进去（症状：名字里出现 `.jpg`）。修法是只看本行找括号、闭合括号认任意宽度，外加兜底"括号里若仍含 `://` 就宁可不要"。

### 4.5 验证方法：门禁本身也会骗人

最后这一类，是我们花时间最多、也最有价值的。

因为本地不能编译、不能看画面、不能跑真机，我们把能离线验证的东西**全部做成了机器检查**——34 道关卡，从"schema 与 Room 逐字节一致"到"枚举 rawValue 唯一"到"README 里的统计数字不能漂移"。

但过程中撞了三个更隐蔽的墙：

**① 门禁会被自己阉割，而且仍然报绿。** 我给一个检查器加新章节时，编辑**插入了一个提前 `return`**，导致后面约 26 项断言变成死代码。症状是断言数从 84 掉到 66，而**所有关卡仍然全绿**——因为报告的数字本身就是从被阉割后的代码里算出来的。

修复之后加了一条机制：**覆盖面自证下限**。断言数低于下限即失败，提示"覆盖可能被阉割，检查是否误插提前 return"。这把"改完要数一遍"的人肉纪律变成了机器检查。

> [!IMPORTANT]
> **一个会自我阉割且仍报绿色的检查器，比没有检查器更危险**——它提供虚假的安全感。

**② 我在读一个没有连到被测对象上的信号。** 连续三次：

| 次 | 发生了什么 | 性质 |
| :--- | :--- | :--- |
| 1 | 变异测试没触发失败 | 工具建了但**没接进 CI**，变异测的是空气 |
| 2 | 补了 CI 引用后重测，仍然"通过" | 编辑**没生效**（锚点写错），而我没先确认 |
| 3 | 两类变异都"exit=0" | 我把 `Out-Null` 打成了 `Out.Null`，管道断了，取到的不是检查器的返回值 |

三次的共同点：**我都在准备根据一个不可靠的信号下结论。**

由此固定了一套次序，此后每次都照做：

```
① 先确认「改动真的生效」（读回文件 / 看输出）
② 跑基线，确认期望值
③ 逐个变异，每个变异都要看到 exit=1
④ 还原，再跑基线确认回到 0
```

**③ 判据取错了树。** 有个脚本统计"交付物行数"并写进 README。它扫的是**磁盘**，于是本机只要存在任何被 `.gitignore` 的文件，统计就比 CI 多；我再用 `--fix` 把多的数字写进 README → CI 立刻红。根因不是"忘了同步"，是**判据取错了树**——CI 只看 checkout 出来的那棵树。现在一律以 `git ls-files` 为准。

现在这套东西长这样：

```bash
python ios/Tools/run_all_gates.py        # 34 道关卡，一次跑完
python ios/Tools/run_mutation_tests.py   # 让关卡自己失败一次，证明它真的在工作
```

第二行是关键。**任何"我验过了"的说法，都需要一个会失败的反例来支撑。**

## 七、最后一点方法

这三个月最大的收获不是写出了多少行 Swift，而是学会了一件事：

**在无法运行、无法观察、无法编译的环境里，"我觉得对"是最贵的三个字。**

所以我们把每一条跨端契约都变成了断言，把每一个检查器都配了会失败的反例，把每一个"不可验证"的判断都重新审了一遍——其中有两次发现是我自己判错了，把可验证的当成了不可验证的。

这条路还没走完。但至少现在，每一次"我验过了"背后都有一个机器在盯着。
